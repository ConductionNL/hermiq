# Changelog

All notable changes to Hermiq are documented in this file.

## Unreleased

### Added

- **Agent tool governance + progressive disclosure + AI Act art.12/14 oversight — the Hermiq consumer side of ADR-063 (`agent-tool-governance-and-disclosure`).** OpenRegister's ADR-063 chain derives a far larger MCP tool catalog (`{app}.{schema}.{search|get|create|update|delete}` per opted-in schema) and serves it through the blessed `ToolRegistryFacade`. Hermiq is its sole agent consumer (ADR-034), and this change closes the three consumer-side gaps a catalog that size opens.

  **Schema-scoped grants with default-deny.** `Agent.tools` stays a `string[]` (ADR-035 D4 froze the shape — no OpenRegister schema migration) but each entry's grammar is extended and resolved by the new `ToolGrantResolver` against the live catalog: an exact id grants that tool verbatim; `{app}.{schema}.*` grants that schema's **read verbs only** (`search`/`get`); `{app}.{schema}.*:write` additionally grants its write verbs; `{app}.{schema}.{verb}` grants exactly that verb. A wildcard can therefore never silently hand an agent `delete` — write/destructive tools must be named explicitly or granted with the `:write` modifier. An empty `Agent.tools` preserves the legacy "all discovered tools allowed" default for every non-derived id, while still stripping classifiable derived write ids. Tool annotations are treated as **untrusted UX signals that only ever restrict** — the authoritative allow/deny stays OpenRegister RBAC at invoke time.

  **Progressive tool disclosure.** When an agent's resolved catalog exceeds `IAppConfig('hermiq', 'tools.disclosureThreshold')` (default **30**), `ToolLoop` places only a single `hermiq.searchTools` meta-tool into the model context instead of every descriptor, and hands the full resolved set to the new `ToolSearchService` for deferred loading. The meta-tool registers through Hermiq's existing `HermiqToolProvider` (`IMcpToolProvider`) so the model calls it with the same mechanism as any other tool, but its **invocation never leaves Hermiq** — `FacadeToolInvoker` short-circuits it straight to `ToolSearchService`, with no facade round-trip. `searchTools` ranks by keyword/description match (v1; embedding similarity deferred) and can only ever return descriptors from the agent's already-resolved, already-default-denied set — disclosure narrows what the model sees, it never widens it.

  **Un-granted destructive invocations route through the human-approval gate.** `FacadeToolInvoker` now checks, at the point of actual invocation, whether a write/destructive-classified tool is part of this run's resolved set. If it is not, it does **not** call `ToolRegistryFacade::invokeTool()` — it creates a pending `Approval` (`sourceType: "tool"`, idempotent on the `agentId` + `toolId` pair) through the existing `human-approval-gate` state machine and blocks. A `denied` decision blocks that pair permanently; an `approved` one lets the next attempt through. This is defense-in-depth at invoke time, independent of whether `ToolLoop` already excluded the tool from context.

  **Per-agent oversight surface (EU AI Act art.12/14).** New `ToolOversightController` + three routes: `GET /api/agents/{agentId}/tool-catalog` (grant-annotated catalog for the editor — `scope`/`destructiveHint`/`granted`/`grantedBy`/`requiresExplicitGrant`, plus whether disclosure is active), `PUT /api/agents/{agentId}/tool-grants` (persists `Agent.tools` via `ObjectService` — single write-path, owner-only, **CSRF guard deliberately left ON** since it mutates an authorization boundary), and `GET /api/agents/{agentId}/tool-invocations` (tenant-scoped invocation rows, newest first, with a retention note and CSV/JSON export). The oversight read sources OpenRegister's richer `mcp.{verb}` AuditTrail entries when present and **degrades gracefully** to the coarser `action='run'` entries when OpenRegister has not shipped them yet — setting `available`/`source` and showing a reduced-detail indicator rather than erroring or fabricating a single row. An agent with no invocations renders an empty state.

  Frontend ships as source (`src/api/toolOversight.js`, `src/components/ToolGrantEditor.vue`, `src/components/ToolInvocationTable.vue`, wired into `AgentDetail.vue`); the webpack bundle and browser verification are deferred.

  Two upstream limitations are documented rather than worked around (both belong to OpenRegister; neither is hand-patched cross-app per gate-27):
  - `McpProviderBridge::getFunctions()` does not forward `destructiveHint`/`scope`/`readOnlyHint` into the descriptor, so write/destructive classification falls back to the **verb suffix** of a 3-segment derived id. A 2-segment/bare (hand-written or legacy) id is never classified this way, so pre-existing whitelist behaviour is preserved exactly.
  - OpenRegister's `createToolInvocationEntry()` records the ambient Nextcloud **session user**, not an agent principal (the `IMcpToolProvider` ABI threads no acting-agent identity into `invokeTool()`). The oversight surface therefore **correlates** invocations to an agent via that agent's owner plus its schedules' owners.

  Adds the `agent-tool-governance` capability spec; extends `human-approval-gate` with the `sourceType: "tool"` requirement; `Approval` schema gains `toolId` and the `tool` source type (v0.3.0), `Agent` gains the documented grant grammar on `tools` (v0.2.0).
